Design reference

Building Fabricate screens

Every primitive rendered at its canonical geometry, in the shipped palette, with the API it needs to be built — then the recipes that assemble them into the three screens this app actually has.

00

How to use this

Read the foundations once. After that, work from section 13 backwards: find the screen archetype you are building, follow its recipe, and open a part's entry only when you need its API.

The five rules that keep screens consistent

1 · One component per job

Where two surfaces do the same thing, they import the same component. If you are about to write a second version, the answer is a prop on the first.

2 · Geometry comes from the ladder

Six control heights, five radii, one 4px spacing scale. A value off the ladder is a bug, not a decision.

3 · Colour is data, not decoration

A tint identifies an entity; a semantic family reports state. Never a literal — a raw rgba() fails the colour gate.

4 · Every control declares its states

Rest, hover, focus-visible, disabled — and where they apply, readonly, invalid, loading, empty. Naming is a required prop, not an optional one.

5 · Foundry owns the window

Container queries, not viewport. Portalled popovers, not CSS offsets. No URL, no router, no toast. Section 05 is not advice.

Hit targets, naming, announcement

24×24 minimum
The hit area may exceed the painted area. A 2px divider still gets a 24px handle; a bare × is 24px around a 9px glyph.
Naming
  • Any control whose visible text is a glyph or a number takes its accessible name as a required prop.
  • A name composed from a value — “increase quantity to 3” — is derived by a shared helper, because 23 call sites drifted the last time it was not.
Announcement
  • A change with no visible focus consequence is announced. Reorder says “Moved {name} to position {n} of {total}”.
  • Order matters: move focus first, then announce — polite speech is cancelled by a focus change.
Motion
  • 140ms ease for a control state change. Nothing else animates.
  • Under reduced motion every transition is removed — canonical, implemented, and gated by a mount test.
The minimum is 24×24, and the hit area may exceed the paint. 05

Foundry contract

Everything here renders inside Foundry's CSS, inside its event handling, inside a window it owns. Six constraints bind the whole set — none of them optional.

Keyboard escape

Foundry recognises focus only in form controls, contentEditable, or a button with a form. Any other focusable element handling arrows, Page or Home/End MUST carry the keyboard-focus opt-out, or the keypress also pans or zooms the canvas. Space on a bare button pauses the game for the whole table.

Listbox focus model

A popover keeps DOM focus in its search input and drives selection with aria-activedescendant. Roving focus onto option buttons is forbidden — it re-arms the canvas bindings.

Floating surfaces portal

Core clips at .window-content and the manager adds two more boundaries, so an absolutely-positioned panel cannot escape by CSS. Portal to .fabricate-manager — never document.body, which loses window stacking — then measure, flip and clamp.

Core CSS collisions

Core's V1 resets do not protect V2 apps. Every button sets its own height and min-height; every input its own width; radio and checkbox need their pseudo-elements removed as well as appearance:none; and the serif ladder must name the element it renders on, because bare headings take core's colour and margins.

Transient feedback is core's

ui.notifications owns it — 83 call sites and a progress-handle API — and core renders its toasts over the module window anyway. Fabricate ships no toast. Destructive confirmation defaults to confirmDialog; the arm-then-confirm pattern is a carve-out for high-frequency row actions and for bulk actions that state impact in-panel.

There is no URL

Foundry's client is a single page with no router. Page state, filter state and navigation live in an app-level store. An in-app href either does nothing or navigates the game away and disconnects the client. Every breakpoint is an @container query, and a container query adds no specificity — so declare the narrow case after the wide one.

Sets & groups

The container layer above the row. An ingredient set holds what a craft consumes; a result group holds what it produces. A recipe may carry several of each, and the resolution mode decides which set routes to which group.

The two containers

Both hold the same rows and the same choice groups. They differ only in the kinds their rows offer and in what a choice inside them means.

A choice group here is the player choosing their reward — the same control, the other side of the craft. This is why a group is not an ingredient-only idea.
One group is awarded per attempt. Whichever mode routes, exactly one result group is produced by a craft — no mode awards two. That is what makes a result group the unit of routing rather than the individual result rows inside it.

Routed by ingredients

The set the crafter satisfies decides the group. Each set names exactly one group; several sets may name the same one.

Set ASteel Ingot ×2 · Oak Haft ×1produces

Set BIron Ingot ×2 · Oak Haft ×1produces

Set CScrap ×4produces
Plain blade
Sets B and C both produce Plain blade. The mapping is many sets to one group and never one set to several: a set that named two groups would leave the engine no way to pick between them.

The mapping is authored here, on the set. Each row carries a select naming its group, tinted to match, so the whole routing is one readable column rather than a field buried in each set’s own editor. Adding a set or a group is a dashed adder beneath the list, and a new group appears immediately in every select above it.

Routed by check

The check outcome decides the group. Each tier names a group, and several tiers may name the same one.

Success and Partial both produce Fine blade, so a group is reused rather than duplicated. The tier list is the system’s outcome tiers, not the recipe’s — the recipe assigns groups to them and edits the tiers themselves elsewhere, which the row states rather than implying by omission. Failure tiers route only where the system policy permits it; otherwise a failed check produces nothing and the tier carries no assignment.
Two authoring traps this surface has to show. Fixed tiers own explicit ranges, and a value between two of them that no tier claims is a gap: the roll matches nothing, the craft is rolled but unrouted, and it fails rather than degrading. The editor states that as a blocking issue rather than a warning. And a group referenced by no set and no tier is unreachable — authored, valid, and never producible.

Ruled out

Candidates reviewed and declined. Each is either a composition of parts already in the set, one-screen furniture, or a surface Foundry already owns. Kept so the reasoning survives and nobody re-proposes them.

Out<MemberRow>

List row geometry with a portrait in the leading cell — structurally identical to the inline-title row already declined. Compose: ListRow + leading.

Out<ActorPicker>

A pill trigger that opens the popover — which already counted it as one of its four callers. Compose: trigger + SearchPopover.

Out<AddButton>

Dashed is a role on the button that owns the meaning. “Sits in flow with its collection” is a usage rule, not a boundary. Compose: Button role=dashed.

Out<RailCard>

A composition that also smuggled back the 34px button size the set retires by name. Compose: Well + Kicker + Button.

Out<FeatureCard>

Two absent props on an identical shape is a props difference, not a distinction. Compose: OptionCards, non-interactive.

Out<PremiumPanel>

A screen, not a primitive. Its one original claim is copy — a product decision — and binding copy to a component makes the offer untranslatable. Canon also forbids any premium signal in the player window.

Out<BoundsInput>

“Two steppers with a rule between”, by its own spec. Compose: two Steppers.

Out<CurrencyInput>

A composition, and wrong about the domain: it assumed a flat world-scoped coin ladder where the model defines a per-system acyclic denomination DAG. Compose: Stepper + Select.

Out<Toast>

Foundry owns transient feedback and renders its own toasts over the module window regardless. Use: ui.notifications.

OutDestructive panel

Canon makes the dialog the default for manager confirmations; the arm is the carve-out. Use: confirmDialog.

CompositionFive more

Inline-title row, thumbnail tile, full-width CTA, locked preview list, studio footer bar. The thumbnail tile is art on IconChip and the CTA is fullWidth on Button, so both are expressible without a component.

Single-callerModal · Graph canvas

One caller each. Recorded so the app’s near-absence of modals is a decision rather than an accident of scope.
