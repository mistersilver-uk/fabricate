Design reference

Building Fabricate screens

Every primitive rendered at its canonical geometry, in the shipped palette, with the API it needs to be built — then the recipes that assemble them into the four screens this app actually has.

00

How to use this

Read the foundations once. After that, work from section 13 backwards: find the screen archetype you are building, follow its recipe, and open a part's entry only when you need its API.

Every entry declares a STATUS beside its heading, and a heading naming several parts declares one per name. target means the entry is specified and the shipped component does not yet match it, or nothing ships — the specimen is what to build towards, not a description of the tree. shipped means the shipped component matches this specimen's API and geometry. divergent means a recorded decision keeps the shipped component different, and the entry names the issue that decided it. prose is a section that specifies no part. The status is FIDELITY to the specimen; how far a surface has adopted a primitive is a different question, tracked by the source-contract exemptions rather than here. Section 16 carries the divergences that are recorded inline rather than as a whole-entry verdict.

The five rules that keep screens consistent

prose
1 · One component per job

Where two surfaces do the same thing, they import the same component. If you are about to write a second version, the answer is a prop on the first.

2 · Geometry comes from the ladder

Six control heights, five radii, one 4px spacing scale. A value off the ladder is a bug, not a decision.

3 · Colour is data, not decoration

A tint identifies an entity; a semantic family reports state. Never a literal — a raw rgba() fails the colour gate.

4 · Every control declares its states

Rest, hover, focus-visible, disabled — and where they apply, readonly, invalid, loading, empty. Naming is a required prop, not an optional one.

5 · Foundry owns the window

Container queries, not viewport. Portalled popovers, not CSS offsets. No URL, no router, no toast. Section 05 is not advice.

Svelte API convention
  • Name — ariaLabel names the control, required-shaped; a member with a shipped localized fallback keeps it. ariaLabelledBy / ariaDescribedBy are id references; panelLabel / panelLabelledBy name a portalled panel. <part>Label is the text of a named part: its visible text where the part renders text, otherwise its accessible name; <part>AriaLabel only where a part needs both. label is visible text, and may also name the element that renders it.
  • Density — density, default 'default', values per specimen. size names a published ladder rung (control height or art square) and nothing else. No boolean compact as a density; a flag that changes what renders is a variant and stays.
  • Tone — tone; the base set is neutral|subtle|accent|success|info|warning|danger; a member’s further values are its specimen’s.
  • Verb role — a role prop on Button only, its shipped closed set neutral|primary|ghost|danger|dashed|warning. It is the button’s verb role, not the ARIA attribute; no other primitive declares role, so an ARIA role reaches their root through ...rest.
  • Callbacks — onclick on a plain button; onChange(value) on a value control, a boolean one included; onToggle for open/closed and for flipping one item’s membership; onSelect(id) on a menu, tab strip or option list; any other event on plus its name in camelCase, as onPageChange; onChoose only on a requirement chooser.
  • Passthrough — class plus ...rest on the root, spread after class; a fixed sub-element takes <part>Props (object); a per-item hook whose value the primitive computes takes <part>DataAttr (attribute name); an attribute the primitive writes from a declared prop is passed by that prop, never through rest.
  • This list binds every component under src/ui/svelte/components/, and tests/design-system-api-convention.test.js holds it over prop names; a name kept outside it is carried in that gate’s exceptions register with its reason. Values are each specimen’s to state.

05

Foundry contract

Everything here renders inside Foundry's CSS, inside its event handling, inside a window it owns. Six constraints bind the whole set — none of them optional.

Keyboard escape

Foundry recognises focus only in form controls, contentEditable, or a button with a form. Any other focusable element handling arrows, Page or Home/End MUST carry data-keyboard-focus="true", or the keypress also pans or zooms the canvas. Space on a bare button pauses the game for the whole table.

Listbox focus model

A popover KEEPS DOM focus in its search input — or in its trigger, where the search field is suppressed — and drives selection with aria-activedescendant. Roving focus onto option buttons is forbidden — it re-arms the canvas bindings. Shipped: the option rows stayed buttons, took tabindex="-1" and data-keyboard-focus="true", and never receive focus.

Floating surfaces portal

The manager root and its scrolling panels each clip, so an absolutely-positioned panel cannot escape them by CSS. Portalling escapes those; it does not escape core's own .window-content, which is the box the panel is then clamped inside. Portal to the application root — .fabricate-manager or .fabricate-app — never document.body, which loses window stacking — then measure, flip and clamp.

Core CSS collisions

Core's V1 resets do not protect V2 apps. Every button sets its own height and min-height; every input its own width; radio and checkbox need their pseudo-elements removed as well as appearance:none; and the serif ladder must name the element it renders on, because bare headings take core's colour and margins.

Transient feedback is core's

ui.notifications owns it — 83 call sites and a progress-handle API — and core renders its toasts over the module window anyway. Fabricate ships no toast. Destructive confirmation defaults to confirmDialog; the arm-then-confirm pattern is a carve-out for high-frequency row actions and for bulk actions that state impact in-panel.

There is no URL

Foundry's client is a single page with no router. Page state, filter state and navigation live in an app-level store. An in-app href either does nothing or navigates the game away and disconnects the client. Every breakpoint is an @container query, and a container query adds no specificity — so declare the narrow case after the wide one.

A repeated draw is not a third strategy. It is up to N under a roll, differing only in whether the same alternative may come up twice — the same count, the same ceiling, one setting apart. Carrying it as its own strategy gave two ways to author one behaviour: a draw of N without replacement and a rolled up-to-N are the same thing, and only the repeating form was ever distinct. The closed set is two, and the matrix has no cell left to forbid.

Up to N is a ceiling, not a quota — fewer is a legal outcome, and a two-alternative group set to up-to-three is authored rather than invalid. Without replacement, draw N above the alternative count exhausts the bundle rather than erroring.

Replacement belongs to draw alone. It is only meaningful where a selection repeats, so any-one-of and up-to must not render it: a setting with no behaviour behind it invites the GM to hunt for a difference that does not exist.
